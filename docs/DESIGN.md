# libkitchen16 — Design

**Project:** `gr-dos/libkitchen16`  
**Status:** Accepted design; see §7 for decisions  
**Target:** 16-bit real-mode DOS on Intel 8086/8088-compatible CPUs, Open Watcom C  
**License goal:** MIT, with independently implemented and auditable source

## 1. Purpose

libkitchen16 is the optional companion of [libc16](https://github.com/gr-dos/libc16) for what libc16 leaves out by its decision 3: floating point. It is what `perl16` (Perl 3, M3.3 of gr-dos/perl16#12) and Tcl16 need, and it was decided in perl16's `docs/M3-RUNTIME-AUDIT.md`, section 11. It provides:

| Module | Interface | Spec |
|---|---|---|
| `fpc` | the helpers `wcc -fpc` calls for `double` arithmetic, comparison and conversion | `docs/spec/fpc.md` |
| `fmt` | `vsnprintf`, `snprintf`, `vsprintf`, `sprintf`, with exact `%e %f %g` | `docs/spec/fmt.md` |
| `fmtio` | `vfprintf`, `fprintf`, `vprintf`, `printf` over libc16's `FILE` | `docs/spec/fmtio.md` |
| `conv` | `strtod`, `atof`, correctly rounded | `docs/spec/conv.md` |
| `math` | C89 7.5 | `docs/spec/math.md` |

`sscanf` (for Tcl16) is later.

The overarching invariant is libc16's: **unused functionality must impose no code or data cost on a linked executable.** Every function is its own library member, and a program links only what it calls.

## 2. Boundaries

- libc16 never depends on libkitchen16, and links unchanged without it.
- libkitchen16 depends on libc16 for `errno`, for `FILE` output in `fmtio`, for the headers (`<stdarg.h>`, `<stddef.h>`, `<stdio.h>`, `<errno.h>`) and the ABI, and for the startup of any program that uses it. `fpc` links nothing from libc16, and neither does any member that doesn't need `errno` or `FILE`. It is pinned by libc16 version (`scripts/fetch-libc16`).
- libkitchen16 ships its own `<math.h>` and `<kitchen16.h>`. It adds to `<stdio.h>` and `<stdlib.h>` only through `<kitchen16.h>`, never in libc16's headers.

## 3. Conventions followed from libc16

| | libc16 | here |
|---|---|---|
| Toolchain | Open Watcom `2026-10-01-Build`, JWasm v2.20 | the same pins and patches |
| Models | small, compact, large; one library each, from the same sources | `LIBK16.LIB`, `LIBK16C.LIB`, `LIBK16L.LIB` |
| Public functions | `__cdecl` | the same |
| Instructions | 8086 only (`scripts/check-8086`) | the same |
| Tests | DOSBox-X, `cputype=8086`, `tests/run-dos` | the same, with host-oracle corpora |
| Selective linking | an unused member changes nothing (`tests/check-selective`) | the same |
| Link maps | only the program's objects and the libraries (`scripts/check-map`) | the same, for libkitchen16's and libc16's |
| Provenance | a spec before code, clean-room sessions, an audit | the same (decision 6) |
| Versions and releases | `VERSION`, DOS style; a merged change tags `v<VERSION>` and publishes the ZIP and the source archive | the same (`.github/workflows`) |
| Protection of `main` | a pull request, the `ci` check, no force pushes | the same |

## 4. Floating point

Compiling with `-fpc` makes `wcc` call helpers for every `double` operation. libkitchen16 provides them (`docs/ABI.md`, "Floating-point helpers"), with IEEE 754 binary64 semantics: round to nearest even, subnormals, signed zeros, infinities and quiet NaNs; no exception flags, traps or `<fenv.h>`. There is no FPU build.

The formatter and `strtod` do **not** use the helpers. They work on the bits of the `double` with integer arithmetic (a big integer of about 1,100 bits), so that they are exact and so that a program that formats or parses a number links no helper. The math functions are C compiled with `-fpc` and use the helpers.

## 5. Selective linking

A format engine and `strtod` are linked whole by the programs that use them. The floating-point conversions are part of the engine: libkitchen16 has no way to tell, at link time, that a program passes no `double`, because `wcc` leaves no marker for it (checked on our own objects). A program that needs only integers formats them with libc16's `libc16_ultoa` and `libc16_ltoa`, as libc16's decision 3 says. Each of the four string functions and four stream functions is its own member over the shared engine, so `sprintf` does not link `printf`'s stream code.

## 6. Verification

- **Oracles.** The host's C library (through Perl) is the oracle for `fmt`, `conv` and `math`, and the host's IEEE arithmetic for `fpc`. Corpora are generated by scripts in each suite and committed with the expected results; nothing is generated in CI.
- **Conformance bars.** `fpc`: bit-exact. `fmt`, `conv`: bit-exact and digit-exact. `math`: exact where the spec says, within 4 ulps otherwise (and exact powers for `pow`).
- **The emulator.** DOSBox-X with an 8086 core runs every program in every model.
- **Call sites.** `tests/check-abi` compiles fixtures and checks the helper symbols and calls, as libc16 does for its helpers.
- **Similarity audit.** `make audit` compares each member's code with Open Watcom's DOS C library, its software and 8087 math libraries and its emulator, and prints only scores. A member with at least 16 runs and a best score over 0.50 fails.

## 7. Decisions

1. **Open Watcom and JWasm pins** are libc16's. Change them only together with libc16 and GR-DOS.
2. **libc16 is a pinned dependency**, fetched from a release by version and SHA-256 (`scripts/fetch-libc16`), or taken from `LIBC16_ROOT`. Moving the pin is a deliberate change of its own.
3. **Calling convention.** Public functions are `__cdecl`. `double` arguments and results follow `docs/ABI.md`. The helpers keep the conventions Open Watcom mandates for `-fpc`, found by experiments on our own objects.
4. **Floating-point model.** IEEE 754 binary64, no flags. `__FDC` reports a NaN as "greater". `double` to integer conversions are defined for every value (`docs/spec/fpc.md`).
5. **Formatting.** `%e %f %g` are exactly rounded at any precision, from the exact binary value; no `%n`, `%p`, `%a`, C99 length modifiers or wide characters. `int` is 16 bits, so a result longer than 32767 characters is an error (`ERANGE`).
6. **Provenance.** Each module has a behavioural spec before it is implemented. The helpers, the formatting and conversion code and the math functions are written by separate sessions that are given only the spec, the tests, the headers and the build, and read no Open Watcom runtime source, header or library disassembly. The host's C library is a test oracle, never a source. `docs/LICENSE-PROVENANCE.md` records each module. Before the first release an automated similarity audit reports only scores.
7. **Models.** The same three as libc16, from the same sources; an assembly member uses `src/model.inc`. The tiny, medium and huge models are not supported.
8. **Releases.** `VERSION` is DOS style. Merging a pull request that changes it tags and publishes it, as libc16 does.
9. **Delivery.** Small, focused commits.
10. **Stack and size.** Each module's spec states a stack bound. Measured figures are in §8.
