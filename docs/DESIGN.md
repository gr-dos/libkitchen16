# libkitchen16 — Design

**Project:** `gr-dos/libkitchen16`  
**Status:** Accepted design; see §7 for decisions  
**Target:** 16-bit real-mode DOS on Intel 8086/8088-compatible CPUs, Open Watcom C  
**License goal:** MIT, with independently implemented and auditable source

## 1. Purpose

libkitchen16 is the optional companion of [libc16](https://github.com/gr-dos/libc16) for what libc16 leaves out by its decision 3: floating point. It is what `perl16` (Perl 3, M3.3 of gr-dos/perl16#12) and Tcl16 need, and it was decided in perl16's `docs/M3-RUNTIME-AUDIT.md`, section 11. It provides:

| Module | Interface | Spec |
|---|---|---|
| `fpc` | the helpers `wcc -fpc` calls for `double` arithmetic, comparison and conversion | `docs/spec/fpc.md` |
| `fmt` | `vsnprintf`, `snprintf`, `vsprintf`, `sprintf`, with exact `%e %f %g` | `docs/spec/fmt.md` |
| `fmtio` | `vfprintf`, `fprintf`, `vprintf`, `printf` over libc16's `FILE` | `docs/spec/fmtio.md` |
| `conv` | `strtod`, `atof`, correctly rounded | `docs/spec/conv.md` |
| `math` | C89 7.5 | `docs/spec/math.md` |

`sscanf` (for Tcl16) is later.

The overarching invariant is libc16's: **unused functionality must impose no code or data cost on a linked executable.** Every function is its own library member, and a program links only what it calls.

## 2. Boundaries

- libc16 never depends on libkitchen16, and links unchanged without it.
- libkitchen16 depends on libc16 for `errno`, for `FILE` output in `fmtio`, for the headers (`<stdarg.h>`, `<stddef.h>`, `<stdio.h>`, `<errno.h>`) and the ABI, and for the startup of any program that uses it. `fpc` links nothing from libc16, and neither does any member that doesn't need `errno` or `FILE`. It is pinned by libc16 version (`scripts/fetch-libc16`).
- libkitchen16 ships its own `<math.h>` and `<kitchen16.h>`. It adds to `<stdio.h>` and `<stdlib.h>` only through `<kitchen16.h>`, never in libc16's headers.

## 3. Conventions followed from libc16

| | libc16 | here |
|---|---|---|
| Toolchain | Open Watcom `2026-10-01-Build`, JWasm v2.20 | the same pins and patches |
| Models | small, compact, large; one library each, from the same sources | `LIBK16.LIB`, `LIBK16C.LIB`, `LIBK16L.LIB` |
| Public functions | `__cdecl` | the same |
| Instructions | 8086 only (`scripts/check-8086`) | the same |
| Tests | DOSBox-X, `cputype=8086`, `tests/run-dos` | the same, with host-oracle corpora |
| Selective linking | an unused member changes nothing (`tests/check-selective`) | the same |
| Link maps | only the program's objects and the libraries (`scripts/check-map`) | the same, for libkitchen16's and libc16's |
| Provenance | a spec before code, clean-room sessions, an audit | the same (decision 6) |
| Versions and releases | `VERSION`, DOS style; a merged change tags `v<VERSION>` and publishes the ZIP and the source archive | the same (`.github/workflows`) |
| Protection of `main` | a pull request, the `ci` check, no force pushes | the same |

## 4. Floating point

Compiling with `-fpc` makes `wcc` call helpers for every `double` operation. libkitchen16 provides them (`docs/ABI.md`, "Floating-point helpers"), with IEEE 754 binary64 semantics: round to nearest even, subnormals, signed zeros, infinities and quiet NaNs; no exception flags, traps or `<fenv.h>`. There is no FPU build.

The formatter and `strtod` do **not** use the helpers. They work on the bits of the `double` with integer arithmetic (a big integer of about 1,100 bits), so that they are exact and so that a program that formats or parses a number links no helper. The math functions are C compiled with `-fpc` and use the helpers.

## 5. Selective linking

A format engine and `strtod` are linked whole by the programs that use them. The floating-point conversions are part of the engine: libkitchen16 has no way to tell, at link time, that a program passes no `double`, because `wcc` leaves no marker for it (checked on our own objects). A program that needs only integers formats them with libc16's `libc16_ultoa` and `libc16_ltoa`, as libc16's decision 3 says. Each of the four string functions and four stream functions is its own member over the shared engine, so `sprintf` does not link `printf`'s stream code.

## 6. Verification

- **Oracles.** The host's C library (through Perl) is the oracle for `fmt`, `conv` and `math`, and the host's IEEE arithmetic for `fpc`. Corpora are generated by scripts in each suite and committed with the expected results; nothing is generated in CI.
- **Conformance bars.** `fpc`: bit-exact. `fmt`, `conv`: bit-exact and digit-exact. `math`: exact where the spec says, within 4 ulps otherwise (and exact powers for `pow`).
- **Coverage.** About 82,000 corpus lines, all run in every model:
  - `fmt` (34,500 lines) and `fmtio` (13,900) are generated by an exact big-integer model of the conversions, not the host's `printf`. They cover:
    - every flag combination, widths and precisions (with `*`);
    - `%d %i %u %o %x %X` with `h` and `l` (32-bit `long`);
    - `%e %f %g %E %G` at precisions from 0 to 1,100, with ties and other exact rounding cases, powers of ten, subnormals, the limits of the format, infinities and NaNs;
    - the integral fast path, and the 32,767-character limit.
  - `conv` (7,600) covers halfway cases, long digit strings, powers of two and ten, exponent limits and syntax.
  - `math` (9,900) covers each function's special values, `errno`, exact cases and random arguments.
  - `fpc` (16,600) checks every helper bit for bit, subnormals and NaNs included.
- **The emulator.** DOSBox-X with an 8086 core and no coprocessor (`fpu=false`) runs every program in every model. `tests/nofpu` probes for a coprocessor and fails if it finds one, so a library that needed an 8087 could not pass. `scripts/check-8086` rejects any instruction an 8086 lacks, x87 ones included, in the members and the test programs (all but the probe itself).
- **Call sites.** `tests/check-abi` compiles fixtures and checks the helper symbols and calls, as libc16 does for its helpers.
- **Similarity audit.** `make audit` compares each member's code with Open Watcom's DOS C library, its software and 8087 math libraries and its emulator, and prints only scores. A member with at least 16 runs and a best score over 0.50 fails.

## 7. Decisions

1. **Open Watcom and JWasm pins** are libc16's. Change them only together with libc16 and GR-DOS.
2. **libc16 is a pinned dependency**, fetched from a release by version and SHA-256 (`scripts/fetch-libc16`), or taken from `LIBC16_ROOT`. Moving the pin is a deliberate change of its own.
3. **Calling convention.** Public functions are `__cdecl`. `double` arguments and results follow `docs/ABI.md`. The helpers keep the conventions Open Watcom mandates for `-fpc`, found by experiments on our own objects.
4. **Floating-point model.** IEEE 754 binary64, no flags. `__FDC` reports a NaN as "greater": the compiler branches on signed conditions that make `<` and `>=` complements, so at least two of the four relational operators are wrong for a NaN whatever the helper does, and "greater" is the least damaging choice (`docs/spec/fpc.md`, "Comparison"). The compiler also tests only the high 16 bits for comparisons with a literal `0.0`, `!x` and `if (x)`; the spec gives tested idioms for programs that need IEEE results. `double` to integer conversions are defined for every value (`docs/spec/fpc.md`).
5. **Formatting.** `%e %f %g` are exactly rounded at any precision, from the exact binary value; no `%n`, `%p`, `%a`, C99 length modifiers or wide characters. `int` is 16 bits, so a result longer than 32767 characters is an error (`ERANGE`).
6. **Provenance.** Each module has a behavioural spec before it is implemented. The helpers, the formatting and conversion code and the math functions are written by separate sessions that are given only the spec, the tests, the headers and the build, and read no Open Watcom runtime source, header or library disassembly. The host's C library is a test oracle, never a source. `docs/LICENSE-PROVENANCE.md` records each module. Before the first release an automated similarity audit reports only scores.
7. **Models.** The same three as libc16, from the same sources; an assembly member uses `src/model.inc`. The tiny, medium and huge models are not supported.
8. **Releases.** `VERSION` is DOS style. Merging a pull request that changes it tags and publishes it, as libc16 does.
9. **Delivery.** Small, focused commits.
10. **Stack and size.** Each module's spec states a stack bound. Measured figures are in §8.

## 8. Measurements

### Stack

Measured by `tests/stack` on the final library, in each model, with the real `fpc` helpers linked: the stack below the call's stack pointer is filled with a pattern, one call is made with interrupts off, and the lowest byte changed is the high-water mark. The figure includes the call's arguments, its return address and every function below it, the helpers too. The inputs are every value of a set (zeros, subnormals, the limits of the format, 1e22 and 1e300 for the argument reduction, the edges of overflow and underflow, infinities, a NaN) for each function of one argument, every pair of a smaller set for those of two, hard cases of `pow` and `ldexp`, and long, halfway and out-of-range strings for `strtod`, so the error branches and the nested helper calls are in it. `make test` runs it (`tests/stack/cases`; the output of `-v`, in `build/MODEL/tests/stack/*.OUT`, is the table) and fails if a function is over the bound of its spec.

| Function | Small | Compact | Large | Bound (spec) |
|---|---|---|---|---|
| `fpc` helper, the deepest (`__FDM`) | 44 | 48 | 54 | 64 |
| `strtod` | 74 | 80 | 82 | 160 |
| `atof` (one more call) | 84 | 94 | 98 | 160 |
| `snprintf`, the widest format | 494 | 522 | 530 | 900 |
| `fprintf` to a file, all of libc16's `fwrite` and DOS below it | 806 | 846 | 862 | `fmt`'s plus 160 plus libc16's |
| `pow`, the deepest of `math` | 380 | 384 | 396 | 448 |
| `log10` | 364 | 370 | 380 | 448 |
| `sin`, `cos`, `tan` (1e22) | 340 | 352 | 362 | 448 |
| `log` | 342 | 348 | 358 | 448 |
| `atan2` | 300 | 302 | 312 | 448 |
| `sqrt` | 114 | 116 | 120 | 448 |
| `fmod` | 94 | 92 | 94 | 448 |
| `fabs` | 12 | 16 | 18 | 448 |

The helper figures have the measuring function's own 18 bytes taken off. The other `math` functions are between these (`tests/stack` prints each). `fprintf` is measured with interrupts on once DOS has turned them on, so it can include a few tens of bytes of a timer interrupt; every other figure is exact. The `math` bound was 400 before it was measured: `pow` is 396 in the large model, so the bound is 448 (about 50 bytes for a change in code generation), and a program must allow the measured figure.

`strtod` and the `math` functions keep static data (`strtod`'s two big integers, 672 bytes, and an 8-byte result slot for every `double`-returning function), so they are not reentrant.

### Size

Measured by `make size` (`tests/size`): `tests/size/size.c` is linked once per profile, like any consumer, and `tests/size/report` gives what each adds to a program that calls nothing of libkitchen16's (`base`). That is libkitchen16's members and what of libc16 they bring in (`errno`, and for `fprintf` and `printf` the `FILE` output down to `write`). Each cell is image / memory / DGROUP, in bytes:

- **image:** the executable's load image (code and initialised data);
- **memory:** what DOS must give the program to load it, the image plus the minimum allocation;
- **DGROUP:** the near data, which is at most 64 KB.

|---|---:|---:|---:|

| `printf("%g")` (with libc16's `FILE` output) | 5358 / 5406 / 144 | 6002 / 6050 / 144 | 6034 / 6082 / 144 |
| `strtod` | 2364 / 3052 / 704 | 2444 / 3132 / 704 | 2444 / 3132 / 704 |
| `sqrt` | 1432 / 1432 / 16 | 1592 / 1592 / 16 | 1592 / 1592 / 16 |

The `fpc` helpers share one core member (`fdcore`), so the first operation costs about 1 KB and all of them about 2.5 KB. `pow` is the largest single function: it brings in most of the `k_*` kernels, which `exp`, `log`, `sin` and `atan2` share, so a second function costs much less than its own row. The `perl` row is perl16's set, about 30 KB in the large model. `strtod`'s 672 bytes of big integers are uninitialised data in DGROUP. The libraries themselves are 74,752 (`LIBK16.LIB`), 77,824 and 79,360 bytes.

Some things stand out:

- **Arithmetic.** An addition takes about 1.1 ms and a division about 4.9 ms. A comparison or a conversion is a few hundred µs.
- **Formatting.** `%.20g` of a non-integral value, which Perl 3 uses for every number it prints, takes about 25 ms. The integral fast path takes 12 ms. Exact conversion of the extreme values takes most of 0.4 s (`%.17g` of `DBL_MAX` or of the smallest subnormal).
- **`strtod`.** A short decimal takes 20–35 ms, 17 digits 50 ms, and `DBL_MAX`, whose exact conversion uses the widest big integers, 0.84 s.
- **`math`.** Each function takes tens to hundreds of milliseconds. `log`, `log10`, `asin` and `pow` with a non-integer exponent take 0.2–0.4 s, and `sqrt` 0.19 s.

These are the first figures. Nothing has been tuned for speed yet.

### Memory

A program needs the stack figures above, and the DGROUP column of the size table. That column is all of libkitchen16's static data: `strtod`'s two big integers (672 bytes), an 8-byte result slot for every `double`-returning function, and constant tables. Nothing in libkitchen16 uses the heap.
